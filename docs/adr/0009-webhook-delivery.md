# ADR-0009: Webhook delivery and signing

**Status:** Accepted · **Date:** 2026-09-27 · **Updated:** 2026-10-04 (implemented through M4)

## Context

Notifications leave the engine through one channel: a signed webhook consumed by n8n, Node-RED or the PlusClouds notification service. The engine must record delivery status and retry failures. An incident event must never be lost because the engine crashed between writing the incident and sending the event, and an event must never be sent for an incident that was rolled back.

## Options considered

1. **Send from the engine right after committing.** Events are lost on a crash between commit and send.
2. **Transactional outbox.** The engine writes the event row in the same transaction as the incident change; a separate notifier delivers it.

For signing:

1. **Custom HMAC header.** Easy, but every receiver needs custom verification code.
2. **[Standard Webhooks](https://www.standardwebhooks.com/) specification.** An open spec with headers `webhook-id`, `webhook-timestamp`, `webhook-signature` (HMAC-SHA256 over `id.timestamp.body`), and existing verification libraries for many languages.

## Decision

Transactional outbox, signed according to Standard Webhooks.

- **Outbox table** `webhook_outbox (id uuidv7, tenant_id, endpoint_id, event_type, payload jsonb, status, attempts, next_attempt_at, last_error, created_at)`.
- **Delivery:** notifier instances claim due rows with `SELECT … FOR UPDATE SKIP LOCKED LIMIT 100`, send with a 10 s timeout, and record the result. `2xx` is success; `410 Gone` disables the endpoint; everything else retries.
- **Retry schedule:** exponential backoff with jitter (5 s, 30 s, 2 min, 10 min, 30 min, then hourly) for up to 24 h, then `failed`. Failed deliveries raise a self-monitoring alert and are visible in `GET /v1/webhooks/{id}/deliveries`, where they can be replayed.
- **Ordering:** per incident, events are delivered in order (the notifier does not send event N+1 for an incident while N is pending). There is no global ordering.
- **Delivery guarantee:** at least once. Receivers deduplicate on `webhook-id`.
- **Signing secret:** per endpoint, generated by the engine (`whsec_…`), encrypted at rest ([ADR-0006](0006-credential-encryption.md)), shown once. Rotation keeps the old secret valid for 24 h and sends both signatures, as the spec allows.
- **Event envelope:** the same CloudEvents 1.0 shape PlusClouds already delivers from its event pushers (`NextDeveloper\Events\Services\EventEnvelopeBuilder`), so the whole platform has one envelope and one verification routine. There is no per-endpoint payload format.

```json
{
  "specversion": "1.0",
  "id": "0192f7c4-…",
  "source": "/monitoring/<installation_id>/<tenant_id>",
  "type": "monitoring.incident.opened",
  "time": "2026-09-28T10:15:00Z",
  "datacontenttype": "application/json",
  "subject": "<incident id>",
  "data": {
    "account_id": "<PlusClouds account uuid, null when standalone>",
    "object_type": "Monitoring\\Incidents",
    "object": { },
    "device": { },
    "check": { },
    "route": { },
    "actor": null
  }
}
```

| Field | Meaning |
| --- | --- |
| `id` | UUIDv7, generated when the outbox row is written; identical on every retry and equal to the `webhook-id` header |
| `source` | Which engine installation and tenant sent the event. The installation ID is generated at bootstrap and identifies one engine among many reporting to PlusClouds |
| `type` | `monitoring.<object>.<action>`, see below |
| `time` | RFC 3339, UTC with `Z` |
| `subject` | ID of the object the event is about (incident, tenant, webhook endpoint) |
| `data.account_id`, `data.object_type`, `data.object` | Same meaning as in PlusClouds envelopes, so PlusClouds listener `conditions` and pusher templates (`{{data.object.status}}`) work unchanged. `object` is the public API representation of the object |
| `data.device` | Device with type, tags, external IDs and its containment path (parents with their external IDs) |
| `data.check` | Check with plugin, last output and the matched threshold rule |
| `data.route` | Alert route ID, step number and step labels ([F06](../features/F06-notifications.md)) |
| `data.actor` | For acknowledgements and manual resolves: the user's engine ID and external ID; otherwise null |

Event types: `monitoring.incident.opened`, `monitoring.incident.updated` (severity or flapping change), `monitoring.incident.acknowledged`, `monitoring.incident.escalated`, `monitoring.incident.resolved`, `monitoring.incident.commented` (stream only: routes deliver it only when their `match.event_types` names it), `monitoring.incident.renotify`, `monitoring.tenant.device_limit_reached`, `monitoring.heartbeat`, `monitoring.webhook.test`. Grouped notifications ([F06](../features/F06-notifications.md)) carry the grouped incidents as `data.objects`, a list of `{object, device, check}`, with `data.group` (`id`, `key`, `count`) and `subject` set to `group:<id>`. `data.object`, `data.device` and `data.check` are null in a grouped event. `renotify` and `escalated` go only to the route that scheduled them. `data.links.incident` links to the panel when the operator configures a URL template. The SSE stream uses the same types and envelope.

- **Signing:** exactly as PlusClouds' `event_webhook` pusher: `webhook-id`, `webhook-timestamp` (Unix seconds), `webhook-signature` (`v1,<base64 HMAC-SHA256 over id.timestamp.body>`, several space-separated during rotation). The secret format `whsec_<base64>` is shared, so leo4 verifies engine events with the code it already has.

- **SSRF guard:** webhook URLs are resolved and checked against the tenant's allowed destinations at delivery time, not only at creation, so DNS rebinding cannot reach internal addresses.

## Consequences

- No lost or phantom events, at the cost of a few seconds of delivery latency (poll interval 1 s, plus `NOTIFY` wake-up to cut idle latency).
- Receivers must handle duplicates; n8n and Node-RED flows need a dedup step, which the integration guide will show.
- One envelope across PlusClouds and the engine: receivers written for PlusClouds events (n8n, Node-RED, customer code) handle engine events too.
- PlusClouds receives engine events on one leo4 endpoint and re-fires them through its own event system, so its existing listeners and pushers (email and SMS, panel inbox, chat, NATS live stream) deliver them. See [ADR-0012](0012-plusclouds-identity-and-external-ids.md#plusclouds-receiver).

## Implementation notes

The outbox described above is implemented as two tables: `events` holds each event once, and `webhook_deliveries` holds one row per event and endpoint. The router turns events into deliveries; the dispatcher claims and sends them. Notifications of incidents that something upstream could explain wait for `notifier.dependency_grace` before routing ([F05](../features/F05-state-and-incidents.md)). Delivery is polled every second; LISTEN/NOTIFY wake-up is not used yet.
