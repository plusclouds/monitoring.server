# ADR-0015: Tenant configuration source — API or file

**Status:** Proposed · **Date:** 2026-09-28

## Context

Monitoring items (devices, checks, credentials references, routes, webhooks, maintenance windows) are managed through the API and stored in PostgreSQL. We also want **decentralized management**: each engine is the source of truth for what it monitors, PlusClouds only links to it ([ADR-0012](0012-plusclouds-identity-and-external-ids.md)), and an operator should be able to change what an engine monitors by editing a file on that engine, without going through a central system.

A file as the only store was considered and has problems:

- Two writers: the panel and API edit items at runtime while an operator edits the file.
- The engine creates items itself (collector-discovered VMs, auto-registered MQTT sensors, inventory), which cannot be written back into a hand-edited file.
- Nodes in an HA install would need a shared filesystem or a sync mechanism.
- Secrets would sit in files; direct file edits bypass the audit log; one syntax error could stop a tenant's monitoring.
- Usage metering ([F13](../features/F13-usage-metering.md)) needs every change as a database write.

## Options considered

1. **API and database only.** Simple and consistent, but no file-based, git-friendly management.
2. **Files only.** Decentralized and reviewable, with the problems above.
3. **Database as the store, with a per-tenant choice of source: API or file.** Files are an input that goes through the same validation, diff, audit and metering path as API writes.

## Decision

Option 3.

- Each tenant has `config_source`: `api` (default) or `file`.
- **`file` tenants:** the engine reads `<tenant_config.directory>/<tenant>.yaml` (process config), and later optionally a git repository. On change (file watch, or `POST /v1/config/reload`), it validates the whole file, computes the diff against the database, and applies it in one transaction through the same code as `POST /v1/config/apply`. A file that fails validation is not applied: the last good configuration keeps running, and a self-monitoring alert and an event report the error with line numbers.
- **One writer per item.** Items created from the file are marked `managed_by: file` and are read-only through the API (edits return `409` with a `managed-by-file` problem type). The panel still shows them.
- **Always through the API, in both modes:** operational actions (acknowledge, comment, resolve, run now, maintenance windows, device test) and anything the engine discovers or registers itself. Files never own discovered devices, inventory or state.
- **Secrets never appear in files.** A file refers to credentials by name (`credential: bmc-dell-ro`); the secret is set through the API or read from a secret file on the host.
- **Audit:** every applied file change is one audit event per changed item with actor `file` and the file's SHA-256 (or the git commit, later).
- **Scope of a file:** a file owns every item it declares, and items it previously declared but no longer does are deleted (declarative, like Terraform). Items created through the API in a `file` tenant are not allowed, so ownership is never mixed.
- **Moving between modes:** `GET /v1/config/export` produces a valid file from the current state. Switching a tenant from `api` to `file` requires a file whose dry run shows no changes; switching back clears `managed_by: file`.
- **Multi-node:** the file is read by the node that holds the maintenance lock; the result is in the database, so other nodes need no file access.

### File format (outline)

```yaml
version: 1
tenant: acme                          # tenant name or external ID; must match the file name
sites:
  - name: ist-1
    country: TR
    timezone: Europe/Istanbul
devices:
  - name: sw-core-1                   # unique per tenant; the key used for references
    type: network
    address: 10.0.0.2
    site: ist-1
    tags: { rack: a12 }
    template: generic-switch          # checks come from the template
    credentials: { snmp: snmp-ro }
  - name: web-01
    type: web
    address: https://example.com
    depends_on: [sw-core-1]
    checks:
      - type: http
        interval: 30s
        config: { expected_status: [200], keyword: "Welcome" }
        thresholds:
          - { metric: total_ms, warning: { op: ">", value: 800 }, critical: { op: ">", value: 2000 }, for: 5m }
alert_routes:
  - name: critical-to-noc
    match: { severity: [critical] }
    webhook: plusclouds
webhooks:
  - name: plusclouds
    url: https://…                    # signing secret is generated by the engine, never in the file
```

- References between items use **names**, unique per tenant and per kind; engine IDs never appear in files.
- The full schema is published as JSON Schema from the API (`GET /v1/config/schema`), so editors can validate files while they are written.

## Consequences

- Operators who want git-based management of an engine have it, and PlusClouds' panel keeps working for every other tenant.
- The `/v1/config/apply` code path becomes central and must be well tested: file tenants, bulk imports and Terraform (phase 3) all use it.
- `file` tenants cannot be edited from the panel except for operational actions. The panel must show why ("managed by file").
- Names become stable identifiers for file tenants; renaming an item in a file is a delete plus a create, unless the file marks it with `previous_name`.
- Process config gains a `tenant_config` section (`directory`, `watch`).
